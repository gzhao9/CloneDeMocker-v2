**What changed, and why.** The 354a60ba version ran PIT through `RefactoringAgent.run`, so its scope was the union of the layer's
MCI test classes. The baseline therefore changed from layer to layer, and there was no kill matrix. It now follows the owner's
design (A-084, E-008):
- **Baseline once per module, on the original code.** Every test of the module runs. PIT mutates the module's own
  `src/main/java` packages and uses its `src/test/java` packages, with `fullMutationMatrix` and `--threads` (default: half the cores).
  All setups share the baseline: `data/<project>/pit-layers/baseline-<host>.json`.
- **Each layer runs on the same scope** with its diffs applied, and is compared with the baseline mutant by mutant:
  `killedLost`, `killedGained`, and `killersLost` (a mutant still killed, but no longer by some test, which names the test).
  Output: `data/<project>/refactoring/<setup>/pit-layers/<host>.json`.
- **Spill rule:** a multi-MCI layer that fails to compile *or* whose tests fail keeps its first MCI, and the rest move to a new
  layer at the end.
- **Harness:** new opt-in fields `BuildScope.pit_classes/pit_tests` and `ProjectHarness.pit_full_matrix/pit_threads`, plus two
  new Gradle init-script properties. They are off by default, so per-MCI verdicts do not change (46 harness tests pass).
  The per-command timeout is `--timeout-hours` (default 6).

**Pilot (kiota, Terra, layer 1, 3 modules, 9 min in total).** All three baselines PASSED (okHttp 460 mutants, azure 481,
abstractions 494). Every mutant killed in a baseline lists its killing tests; 163 of okHttp's 197 list more than one, so the
matrix is on. All three layer-1 runs passed with 0 kills lost, 0 gained and 0 killing tests lost. The layer really changed
3 test files in okHttp, so these zeros are real.

**Not exercised yet:** a Maven project, and the spill path. On Maven, `-pl X -am` also runs PIT in upstream modules, which then
mutate only classes matching X's packages. That is normally none, so check the first baseline's mutant count for inflation.
Spring projects share package roots across modules.
