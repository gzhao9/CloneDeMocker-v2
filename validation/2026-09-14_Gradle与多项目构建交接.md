Maven 的隔离不是自动发生的。必须在 **compile、test、PIT** 三条命令均传入同一个 `-Dmaven.repo.local=<path>`。当前 `ProjectHarness` 和 `ScopedProjectHarness` 已支持 `maven_repo_local`，请不要在后续改动中丢失这个参数。

Gradle 不能用 `maven.repo.local`；它需要通过子进程环境变量 `GRADLE_USER_HOME=<path>` 隔离缓存。

## 给 Claude 的下一项 Gradle 实现任务

目标不是为每个项目硬编码命令，而是引入一个只读的 `GradleProjectLayout` 探测结果，供 AST 与 Harness 共用。

### 1. 先实现 Gradle layout probe

使用 `gradlew[.bat] --no-daemon --console=plain -I <temporary-init-script> cloneDeMockerLayoutAll`。init script 必须写到系统临时目录，不能写入被分析项目。

探测输出采用每行一个带固定前缀的 JSON，例如：

```text
CLONEDEMOCKER_LAYOUT:{"gradlePath":":core","projectDir":"...","testJavaRoots":[".../src/test/java"],"mainJavaRoots":[".../src/main/java"],"testCompileClasspath":["...jar"],"testRuntimeClasspath":["...jar"],"hasPitestTask":true}
```

要求：

- 遍历 `allprojects`；
- 从真实 `SourceSetContainer` 读取 `main` / `test` 的 Java source roots，不能假设永远是 `src/test/java`；
- 输出真实 Gradle path（如 `:core:foo`）和 `projectDir`；
- 优先读取可解析的 `testCompileClasspath`，必要时再补充 `testRuntimeClasspath`；
- 不存在 Java plugin、source set 或 PIT task 的子项目应输出明确的空值/false，而不是使整个探测失败；
- 命令失败时保留 stdout/stderr，返回 `UNAVAILABLE`，不静默退回全项目测试。

### 2. 用 layout 支持 AST 与类型解析

JavaParser 的 AST 读取本身不依赖 Maven/Gradle：已有的 `src/main/java`、`src/test/java` 扫描足以解析标准项目。Gradle 支持的重点是为非标准 source set 与符号解析补齐准确输入。

- `EnhancedProjectResolver` 接收 layout，而不是自己仅根据根目录是否有 `build.gradle` 来猜测；
- 为 layout 中所有 Java source roots 注册 `JavaParserTypeSolver`；
- 将对应模块的 classpath jar 注册为 `JarTypeSolver`；
- classpath 探测失败时仍允许无依赖 AST 扫描，结果中记录 `dependencyResolution=UNAVAILABLE`；
- 不要把 `build/`、`.gradle/` 纳入源码扫描或类型根。

### 3. 再实现 Gradle 的 MCI → 模块映射与验证

按“测试文件的绝对路径被哪个 `projectDir` 最长前缀包含”确定 Gradle 子项目，返回实际 Gradle path，而不是目录字符串。

验证时按模块分组：

- compile：`:<module>:testClasses`；根项目为 `:testClasses`；
- test：`:<module>:test --tests <fully.qualified.TestClass>`；
- 同一个 MCI 跨模块时，每个模块独立执行并合并证据，不能把不同模块塞入一条 task 命令；
- 每个 Gradle 子进程传入本项目的 `GRADLE_USER_HOME`，并使用 `--no-daemon --console=plain`；
- `--tests` 无匹配时应显式失败或被记录为 no-tests，不能当作通过。

### 4. PIT 采用 capability-based adapter

不能假定所有 Gradle 项目都有 `pitest` task，也不能假定 `-PpitestTargetTests` / `-PpitestTargetClasses` 被构建脚本认识。

- layout probe 或单独 `gradlew tasks --all` 先确认 PIT task；
- 若无 PIT plugin/task，返回 `PIT_UNAVAILABLE`，论文中明确报告，不修改受试项目的 `build.gradle`；
- 若有 task，调用实际模块 task（通常为 `:<module>:pitest`），只传项目已声明支持的筛选参数；
- 收集 Maven 与 Gradle 两类报告路径，并按本次运行时间过滤：`target/pit-reports/**/mutations.xml`、`build/reports/pitest/**/mutations.xml`；
- PIT 证据至少保存 total、killed、survived、mutation score 与逐 mutant 状态，前后比较应基于相同 mutant key。

### 5. 实现顺序与验收

1. layout probe 的 parser + fake multi-module Gradle fixture 单元测试；
2. 文件到 Gradle path 的最长前缀映射单元测试；
3. `ScopedProjectHarness` 的命令构造测试（根模块、子模块、跨模块、无 PIT）；
4. 用队列预热完成后的 Kiota Java 做首个真实集成测试：layout、AST 扫描、指定测试类 compile/test；
5. 再验证 Spring Integration，最后才尝试更大的 Spring Security；
6. 任何 PIT 适配在真实项目中确认 report 路径前，不得在论文中声称 mutation score 保持不变。

这项工作完成前，Gradle 项目可以被检测为“候选受试对象”，但不能和已经验证的 Maven/Dubbo 数据合并计算 RQ2 成功率。
